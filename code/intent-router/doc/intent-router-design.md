# intent-router 实现设计（模块级取舍与实测记录）

> 本文放**实现设计**；跨模块方案、实施计划与验收回填在 `doc/ops-agent-intent-router-plan.md`（AGENTS §10 归属）。
> 使用者视角的说明见插件 `README.md`。

## 1. 挂点选择（为什么不选别的）

| 目的 | 挂点 | 结论 |
|---|---|---|
| 改写/注入用户消息 | waterfall **`agent/pre-step`** | **选它**。它能拿到本步从 inbox 取出的 `UserMessage[]`，可返回 `{kind:'enter', messages:[...]}` 整体替换/追加；上游 `tool-skill` 的确定性注入就是这个用法（`packages/skill/tool-skill/src/index.ts:177-204`） |
| 按意图换模型 | `agent/request` | 未采用（v1 不需要；留待后续） |
| 不经模型直答 | `llm/stream` 短路 | 未采用。用户拍板 v1 只注入提示；且上游 bridge 依赖 attempt 帧判终局，短路是更大的行为改动 |
| 工具调用拦截 | `tools/pre-execute` | 不合适：上游明确不支持改写参数，且拦不到"用户消息→模型"这一步 |
| HTTP 层前置 | ops-api `handleChat` | 不合适：只有 HTTP 面生效（GUI 会话覆盖不到），且该层拿不到服务端完整历史与模型选择权 |

选 DSH 插件 + `agent/pre-step` 的额外收益：ops-api 一行都不用改。

## 2. 第 2 层算法选型（调研结论）

按"先便宜后贵"串成链，逐段复用项目已有实现，不引入新依赖：

| 段 | 手段 | 复用来源 | 实测耗时 |
|---|---|---|---|
| 2a | 口语别名 → 规范 ID → 意图 | `dsh-plugin/constants.ts` 的 `SYMPTOM_ALIASES`/`ERROR_ALIASES`（56 + 20 条） | <0.5ms |
| 2b | BM25 原型打分（CJK 单字+bigram 分词） | `dsh-plugin/bm25.ts`（零依赖纯函数，单点转出见 `bm25.ts`） | <2ms |
| 2d | RRF 融合（k=60）+ 置信门 | `dsh-plugin/bm25.ts` 的 `rrfFusion` | <0.1ms |
| 2c | 向量相似 | 新增 `embed.ts`（BGE sidecar） | ~85ms/查询 + 5s 启动预热 |

**刻意不引入**：编辑距离/Aho-Corasick/小型分类器——别名表 + BM25 已覆盖"口语同义"，多一个算法就多一份调参与漂移。

### 门限指标为什么是「绝对分 + 相对间隔」而不是「份额」

标定过程（24 条标注集，`eval/questions.json`）：

1. 初版用「份额 = top1 / 正分总和」+ 份额间隔，阈值 0.35。结果**大面积误杀正确样本**：23 条意图共享大量通用词，正确命中的份额也只有 0.22~0.50。
2. 换指标后的实测分离度：
   - 采纳组：top1 最小 17.6（"Oracle 到 MySQL 支持吗"），相对间隔最小 **0.395**
   - 放弃组：top1 最高 19.1（"创建规则"，间隔 0.21 拦住），间隔最高 0.52（"能不能便宜点"，绝对分 10.4 拦住）
3. 因此取 **minBm25Score=16 + minBm25RelMargin=0.35**：两个门限**互补**，缺一即误判（`eval-intent.ts --sweep` 可复现这条结论）。

### 语料词卫生（一次真实误判换来的）

"能不能便宜点" 曾被误采纳为 `check_action_risk`——根因是 `keywords` 里塞了模态疑问词（"能不能/可以吗/支持吗"），
它们在任意问句里都出现，匹配上就当成意图证据。修法：
- 生成器里剔除模态疑问词与泛化动词（怎么/如何/准备/建议…），只保留领域判别词；
- SKILL.md 的**泛化触发器**入拒绝表（"看日志/看规则/规则状态"…），因为它们跨意图通用；
- 实测："能不能便宜点" 的 BM25 分从 15.5 降到 10.4（落到绝对分下限之下）。

### 症状 Owner 的取舍

`SYMPTOM_OWNER` 把每个症状归到**唯一** owner：别名索引对"多意图共享的 ID"直接不收（歧义别名只会制造误判）。
`connection_error` 刻意归到**工具**意图 `diagnose_db_link` 而非 skill 意图——① 领域里本就有这个工具，注入"调用 diagnose_db_link"比"加载某 Skill"更可执行；
② 症状类 skill 意图彼此语义相邻，每多一个就多一个抢票者，间隔被拉平后门限集体拒绝（实测挪走后连不上类的间隔才够）。

## 3. 顺序补救：向量只做补救，不接管

**第一版设计是错的**：把两路的分数一起 RRF、再由向量分支判定，等于让向量"接管"门限。
实测代价：采纳率从 12/13 掉到 **8/13**——BM25 明明有把握的样本被向量不足 0.62 的余弦误杀；而向量也没救回 BM25 判不出的样本。

改成**顺序判定**：

```
层 1 规则 → （命中即采纳，不碰 BM25 与向量）
强别名   → （命中即采纳）
BM25 门限 → 有定论即采纳（**完全不调用向量**，热路径 ~1ms）
BM25 判不出 且 存在重叠 → 才调用向量，要求 余弦过线 + 间隔够 + BM25 前 2 名互证
都不行   → 不表态，交回主模型
```

收益：热路径在多数输入上仍是微秒级（自测断言"BM25 有定论时向量调用次数为 0"）；
且不会因为向量而丢掉本来能识别的意图。跨方法互证（`vectorCorroborateTopK=2`）是拦住
「看下日志 → search_qdrant（cos 0.669）」这类短泛化输入的最有效手段。

## 4. 三条安全网（误识别的兜底）

1. **门限**：分数 + 间隔双门限，且采纳标准是"零误采纳优先"——宁可拒（等于现状）不可错（注入错误提示比不注入更糟）。
2. **免责声明**：注入文案固定带"该提示由本地规则/算法得出，若与用户意图不符请以用户输入为准"。
3. **默认 observe**：先只记录、量化误识别率，再决定是否切 `inject`。

另有两条工程兜底：注入按 `session+turn` 去重（同回合只注入一次）；`overrides.ts` 是唯一手改入口，生成物禁手改。

## 5. 向量路径复核（要重新评估时按此执行）

```sh
# ① 两组样本：标注集 24 条 + 同义改写 9 条（脚本内 PARA 表）
node --import tsx/esm /hdd/demo/public/dsh-info/code/scripts/eval-intent.ts --with-vector
# ② 若仍无救回，尝试「每条原型单独向量 + 取最大相似度」（当前实现是每意图一段语料一个向量）
#    实验脚本与数据见 doc/ops-agent-intent-router-plan.md §验收 的 V 系列
```

判定标准：**至少要有样本出现"BM25 判不出、向量判对"**，且放弃组仍为零误采纳，才值得把 `useVector` 打开。
2026-10-08 的实测是不满足（0 条救回 + 短问法余弦不可分），故默认关闭。

## 6. 已知限制

- 层 1 刻意只覆盖错误码/寒暄/显式工具名：操作类问句（"如何创建规则"）在 `resolve_operation` 与 `get_prerequisites` 之间
  天然歧义，交给层 2 的门限与主模型，不在层 1 硬判。
- 显式点名的 **Skill 名**（如 `i2stream-log-analyzer`）被多个意图共享时不表态（歧义）；`/skill` 手势归上游 `tool-skill`，本插件不重复接管。
- 标注集只有 24 条（领域内自建），门限与原型仍需用线上观测数据持续校准。
- 注入消息会进入会话历史（与上游 skill 注入同理），因此文案保持简短。
